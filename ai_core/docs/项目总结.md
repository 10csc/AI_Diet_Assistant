# AI 饮食助手 — 两级模型管线的工程化实践与反思

一次关于 RAG 知识库、两级模型编排、C++ 嵌入式服务器与本地推理加速的完整项目复盘。

## 前言

这是一个全栈 AI Web 应用项目，目标是做一个**智能饮食推荐系统**：用户输入自己的身体状态、天气、口味偏好，系统通过两级 AI 模型管线分析营养需求、检索食材知识库，最终生成个性化的中国菜式推荐。

项目要求能在本地运行（Windows 环境），同时支持云端 API（DeepSeek）和本地模型（Ollama / llama.cpp）两种推理后端。前端不需要复杂的交互，一个对话式的聊天界面就够了。

发布时不需要任何费用，用户只需自己准备 API Key 或本地模型。

## 最终结果

项目完成了一个完整的饮食推荐 Web 应用：

- **前端**：单页面聊天界面，支持天气配置、个人信息设置、历史对话管理，响应式布局
- **C++ 后端**：自实现的 HTTP 服务器（基于 WinSock），负责静态文件服务、请求路由、调用 Python 引擎
- **AI 引擎**（Python）：两级模型管线 + RAG 知识库
  - 一级模型分析用户输入（身体状态、心理状态、营养素需求）
  - RAG 中间层从食材知识库检索匹配食材
  - 二级模型生成完整菜式推荐（主菜 + 配菜）
- **多后端支持**：Ollama 本地模型、DeepSeek API、llama.cpp（直接加载 GGUF）

一级模型使用 Qwen3.5-2B GGUF（llama.cpp 加载），在 RTX 3050 4GB 上全量 offload 后推理耗时约 10 秒（含首次 CUDA 编译），二次推理约 2-3 秒。二级模型使用 DeepSeek API，端到端完整管线约 15-20 秒完成一次饮食推荐。

## 项目分工

单人项目，不存在分工问题。但工作量分布大致如下：

- **AI 管线设计**（两级模型 + RAG 知识库）：约 70% 的时间
- **C++ 服务器**（从零手写 HTTP Server）：约 10% 的时间
- **前端调试和对接**：约 10% 的时间
- **杂项**（启动器、配置、文档、llama.cpp 编译折腾）：约 10% 的时间

实际上最耗时的不是写代码，而是理解和调整模型输出的格式——如何让模型稳定输出 JSON，以及如何处理模型输出中的思考标签（`<think>`）。这些看似简单的问题花了大量时间调试。

## 数据处理

### 1. 食材知识库的选择

项目使用一份公开的「食物成分表」Excel 文件作为唯一的知识来源。文件包含约 2568 条食材条目，涵盖能量、蛋白质、脂肪、膳食纤维、维生素、矿物质等营养字段。

一开始考虑过自己整理菜谱数据，但发现（1）品种太多，（2）标准不统一（比如番茄炒蛋的"一人份"怎么定义？），所以放弃了。最终还是只用食材营养表做 RAG。

### 2. 知识库构建

使用 ChromaDB 作为向量数据库，embedding 模型选用 `BAAI/bge-small-zh-v1.5`。如果 sentence-transformers 不可用，回退到 MD5 哈希向量（虽然精度低，但至少不会让程序崩溃）。

知识库被设计为运行时自动构建——启动时检查 Chroma 索引是否存在，不存在则从 Excel 重建。这个设计在后续重构时带来了一个小麻烦：路径改过之后，旧的索引缓存和新路径对不上，需要手动删除缓存重建。

有个教训：Excel 里的字段名包含中文（如"蛋白质_g"、"能量_kcal"），在代码里直接硬编码这些字段名做条件筛选不是好做法。应该在加载时做一层字段名规范化映射，避免后续改动 Excel 时代码跟着坏。

### 3. RAG 召回策略

RAG 的检索关键词来自一级模型的分析输出。一级模型会根据用户输入推断出「需重点关注营养素」「检索关键词」等字段，然后用这些字段去 ChromaDB 做向量检索。

检索回来的食材再按置信度排序、缺失字段打分，最终选 8 个左右作为二级模型的参考食材。这个流程看起来合理，但实际效果很大程度上取决于一级模型输出的质量。如果一级模型输出的检索关键词不够准确，RAG 就等于在乱找。

## 模型架构

### 1. 两级模型管线

```
用户输入 → 一级模型（分析） → RAG（检索） → 二级模型（推荐）
```

这个架构的设计动机很简单：**任务分离**。让一个模型同时做用户画像分析和菜谱推荐的话，提示词太长了，而且两个任务对模型能力的需求不同——分析需要结构化的 JSON 输出能力，推荐需要烹饪知识。

一级模型使用小模型（2B）就够了，二级模型用大模型（云端 DeepSeek）来保证推荐质量。这个搭配在成本和效果之间找到了一个不错的平衡点。

### 2. 提示词设计的曲折

提示词的设计经历了多次迭代：

- **第一版**：用原版 `PRIMARY_ANALYSIS_PROMPT`，让模型输出 7 个固定字段的 JSON。在大模型上（DeepSeek-chat）工作良好。
- **第二版**：切换 Ollama 本地模型（deepseek-r1:7b）后发现，模型经常输出思考过程再输出 JSON，`parse_preprocess_result` 的 fallback 解析器能勉强处理，但很不稳定。
- **第三版**：换用 llama.cpp + Qwen3.5-9B，遇到更大的问题——模型是「思考型」的，输出都包在 `<think>` 标签里，且思考内容远超最终的 JSON 输出。不得不写 brace-matching 逻辑来提取最后一个完整 JSON。
- **第四版**：换 Qwen3.5-2B 后，大模型的 prompt 对这个 2B 模型太复杂了，模型直接输出 `speechless` 拒绝回答。只能为小模型单独写了一份精简版 prompt。

**教训**：不同模型对 prompt 的遵循能力差异比想象中大得多。在 70B 模型上完美工作的 prompt，到 2B 模型上可能完全无法使用。如果项目需要支持多种模型后端，每个后端可能需要独立的 prompt 适配层。

### 3. llama.cpp 接入的血泪史

这是整个项目里最折腾的部分。

一开始用的 Ollama，但用户听说了 Ollama 对模型性能的「阉割」传言，要求直接用 llama.cpp 加载 GGUF。

**第一关：编译**

用户的 CUDA 版本是 11.8，但 llama.cpp 的预编译二进制只提供 CUDA 12.4 版本。从源码编译遇到了 CUDA 注册表缺失（CUDA 安装在非默认路径 F:\CUDA）和 MSVC 工具链找不到的问题。最终通过 VS2022 开发者命令提示符 + 显式指定所有 CUDA 路径解决了。

**第二关：模型选择**

一开始选的是 `Qwen3.5-9B-DeepSeek-V4-Flash-Q3_K_S.gguf`（9B 参数，约 4GB）。在 RTX 3050 4GB 显存上只能 offload 28/33 层到 GPU，首次推理耗时 3 分钟以上。后来换成 Qwen3.5-2B Q4_K_M（约 1.2GB），全部层都能 offload 到 GPU，首次推理 10 秒，二次推理 2-3 秒。**结论：2B 模型在这个场景下比 9B 实用得多。**

**第三关：接口设计**

最初把编译好的 `llama-server.exe` 和 DLL 直接放在了项目目录的 `llamacpp_bin/` 里。但这个二进制是绑定在用户机器上的（CUDA 11.8 + VS2022 编译），别人用不了。后来改为纯 HTTP 客户端模式——就像 Ollama 一样，用户自行启动 `llama-server`，项目通过 HTTP API 连接。

**第四关：端口冲突**

多次测试后，后台积累了 9 个残留的 `llama-server` 进程，全部占着同一个端口。每次测试新模型时都在连接到旧进程，导致输出始终不对。最终靠 `wmic` 按 PID 逐个杀掉才解决问题，并在代码里加入了端口检查和随机端口回退逻辑。

## 系统集成

### 1. C++ 后端

后端从零手写，使用 WinSock API 实现 HTTP 服务器。单文件 `backend.cpp` 约 1400 行，包含：

- HTTP 请求解析和路由
- 静态文件服务
- Config.json 和 config.txt 双配置格式支持
- 通过临时 JSON 文件调用 Python 引擎
- 日志轮转和保留期管理
- 历史对话管理

用 C++ 而不用 Node.js 或 Python 的原因：用户觉得 C++ 更"轻量"、启动快、依赖少。实际做下来，手写 HTTP 服务器的坑很多（URL 编码、MIME 类型、分块请求等），但确实做到了零外部依赖——只需要 Windows 自带的 ws2_32 库。

### 2. Python AI 引擎

`main.py` 是核心编排入口，通过 `--request_file` 接收 JSON 输入，返回 JSON 结果。整个过程是同步的，但加入了自动重试和指数退避。

RAG 知识库位于 `rag/nutrition_kb.py`，使用 ChromaDB 做向量检索。embedding 模型在首次运行时自动下载，之后缓存到本地。

### 3. 启动器

C# 写的启动器（`launcher_source.cs`），负责：

1. 检查项目文件完整性
2. 自动停止旧的后端进程
3. 准备 Python 环境（检测 venv）
4. 检查是否需要启动 Ollama
5. 编译 C++ 后端（首次运行时）
6. 启动后端并打开浏览器

启动器本身也被编译成 exe，双击就能运行整个项目。

### 4. 项目结构治理

项目的目录结构经过一次大重构：

- `AI_Demo/` → `ai_core/`（消除 "Demo" 误导）
- `Demo/` → `server/`（明确职责）
- 数据文件归入 `data/`
- 启动器源码归入 `launcher/`
- 配置文件模板化（Config.example.json）
- API Key 脱敏后写入日志

这个重构本身也产生了一些教训：路径变动后需要同步更新 10+ 个文件中的引用，稍微漏一个就会导致运行时错误。

## 安全问题

项目有一道明显的安全隐患：API Key 的管理。

DeepSeek API Key 一开始硬编码在 `Config.json` 里，而这个文件还被提交到了 git。密钥随后在日志中出现了 3 次（因为 `save_to_jsonl` 把完整的 `model_id`——包含 API Key——写入了日志）。

**修复：**
- `Config.json` 加入 `.gitignore`，创建 `Config.example.json` 模板
- `main.py` 的 `save_to_jsonl` 函数加入对 `model_id` 的自动脱敏
- 建议用户注销旧 Key 并重新生成

这个问题其实在项目初期就该处理好，拖到最后才修。如果项目被公开，Key 的泄露可能会导致经济损失。

## 效果

项目可以正常完成从用户输入到饮食推荐的完整流程。以下是成都地区、28 岁男性、偏瘦体质、疲劳状态下的一次推荐示例：

**一级模型分析结果（llama.c项目总结p Qwen3.5-2B）：**
```
用户画像摘要：28岁男性，身高175cm，体重70kg，体型偏瘦，偏好清淡口味
身体状态分析：近期感觉疲惫，可能存在能量摄入不足或代谢偏低
需重点关注营养素：蛋白质、复合碳水化合物、B族维生素
饮食限制：避免高油高盐重口味
```

**RAG 检索结果：** 成功召回豆腐丝（蛋白质 57.8g）、火鸡胸脯肉（蛋白质 22.4g）、基围虾等优质蛋白来源。

**二级模型推荐（DeepSeek API）：** 生成主菜 + 1-2 道配菜的完整菜式推荐。

但目前还有一些可以改进的地方：

- 一级模型输出的字段稳定性还有提升空间，偶尔格式不对
- 4GB 显存的 RTX 3050 跑 2B 模型是在够了，但不能同时跑其他 GPU 任务
- DeepSeek API 的延迟不稳定，有时 3 秒有时 15 秒

## 总结与反思

做这个项目最大的感受是：**AI 应用开发真正的难点不在模型本身，而在模型周围的那一圈工程**。

让模型输出 JSON，看起来简单，实际上花了整个项目 1/3 的时间。跨版本切换模型（Ollama → llama.cpp → 不同参数的 GGUF）的适配，一个比一个折腾。

另一个教训是安全问题最容易在前面忽视、在后面爆炸。API Key 硬编码和 git 提交的问题应该是一个常识性的红线，但还是踩了。

如果现在重新开始这个项目，我会做几个不同的选择：

1. 一开始就设计好「多后端适配层」——每个模型后端有独立的 prompt 和解析逻辑，而不是在 `PREPROCESSOR_MAP` 里简单加一个函数就完事。
2. 日志系统从一开始就假设它会包含敏感信息，提前做脱敏。
3. 在前端和后端之间加入一个简单的中间表示层，而不是把 `model_id`（内含 API Key）直接全文透传。
4. 也许不该手写 C++ HTTP 服务器——虽然学到很多，但用成熟的方案（如 Flask/FastAPI）能省下至少一周的时间。

当前项目已经可以在本地正常运行。后续如果要继续迭代，优先级最高的应该是菜谱知识库的补充和二级模型推荐质量的提升，而不是继续折腾推理后端。
