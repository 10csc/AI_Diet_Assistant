# AI 饮食助手 RAG 知识库设计

## 1. 目标

本项目的知识库不再只服务于“按口味推荐菜”，而是服务于以下链路：

1. 一级模型先输出用户营养需求分析
2. 中间层将“用户所需营养”转换成“符合偏向的食材候选”
3. 二级模型结合检索证据生成最终菜式推荐

核心目标：

- 支持“用户当前需要什么营养”的检索
- 支持“用户想吃哪一类食物”的分类检索
- 使用真正的向量数据库承载食材召回

## 2. 数据来源

当前知识库主要来自 `食材营养.xls`，包含三类数据：

- `食物成份表`
- `新食物成份表`
- `标准体重表`

其中：

- 前两张表用于构建食材营养事实库
- `标准体重表` 用于辅助判断体型状态、估算标准体重

## 3. 分层设计

建议知识库分为三层：

- `原始层`
  - 直接从 `xls` 导出的结构化 JSON
  - 保留表名、原始字段名、原始行内容

- `标准化层`
  - 将不同工作表字段映射为统一字段
  - 字段示例：
    - `name`
    - `region`
    - `energy_kcal`
    - `protein_g`
    - `fat_g`
    - `fiber_g`
    - `carb_g`
    - `vitamin_a_ug`
    - `vitamin_b1_mg`
    - `vitamin_b2_mg`
    - `niacin_mg`
    - `vitamin_e_mg`
    - `vitamin_c_mg`
    - `sodium_mg`
    - `calcium_mg`
    - `iron_mg`
    - `cholesterol_mg`

- `检索层`
  - 为每条食材文档补充分类标签、搜索文本、检索向量或稀疏向量
  - 保留后续接入 embedding 模型所需的 metadata

## 4. 分类体系

知识库分类不能只依赖 `xls` 原始类别字段，必须同时兼容界面图片中的业务分类。

建议采用双分类：

- `raw_category/raw_class`
  - 来自原始表格
  - 用于保留数据出处

- `image_category/image_subcategory`
  - 对齐当前界面分类体系
  - 例如：
    - `谷类及制品`
    - `薯类、淀粉及制品`
    - `干豆类及制品`
    - `蔬菜类及制品`
    - `菌藻类`
    - `水果类及制品`
    - `坚果、种子类`
    - `畜肉类及制品`
    - `禽肉类及制品`
    - `乳类及制品`
    - `蛋类及制品`
    - `鱼虾蟹贝类`
    - `婴幼儿食品`
    - `小吃、甜饼`
    - `速食食品`
    - `饮料类`
    - `含酒精饮料`
    - `糖、果脯和蜜饯、蜂蜜`
    - `油脂类`
    - `调味品类`

这样做的好处：

- 前端筛选、展示、推荐逻辑统一
- 检索时既能按“营养需求”召回，也能按“食物类型”约束

## 5. 文档切分策略

食材知识不建议按大段文本切分，建议采用“单食材单文档”。

单条文档建议包含：

- 食材名
- 地区
- 图谱分类
- 关键营养指标
- 来源工作表

示例：

```json
{
  "name": "鸡腿",
  "image_category": "禽肉类及制品",
  "image_subcategory": "鸡",
  "protein_g": 16.4,
  "fat_g": 13,
  "iron_mg": 1.5,
  "sodium_mg": 6,
  "source_sheet": "新食物成份表"
}
```

## 6. 中间层定型

中间层只做一件事：

- 输入：用户所需营养
- 输出：符合偏向的食材候选

推荐输入结构：

```json
{
  "user_state_summary": "",
  "body_status": "",
  "mental_status": "",
  "target_nutrients": [],
  "dietary_limits": [],
  "preferred_categories": [],
  "retrieval_keywords": []
}
```

推荐输出结构：

```json
{
  "food_candidates": [
    {
      "name": "",
      "image_category": "",
      "image_subcategory": "",
      "nutrition_hits": [],
      "match_reasons": [],
      "risk_notes": [],
      "nutrition_snapshot": "",
      "coverage_score": 0.0,
      "confidence": 0.0,
      "available_fields": [],
      "missing_fields": [],
      "missing_relevant_fields": []
    }
  ],
  "candidate_count": 0,
  "output_description": ""
}
```

## 7. 检索策略

当前实现建议使用三段式检索：

1. 规则解析
   - 从一级模型输出中提取：
     - 用户画像摘要
     - 身体状态分析
     - 心理状态分析
     - 目标营养素
     - 饮食限制
     - 检索关键词

2. 召回
   - Chroma 中文语义向量召回
   - 分类偏好过滤或加权
   - 检索关键词匹配

3. 重排
   - 营养素覆盖度加权
   - 饮食限制惩罚
   - 分类偏好加分
   - 数据完整度加权
   - 缺失关键字段谨慎降权

## 8. 缺失值处理策略

缺失值原则：

- 缺失不等于 0
- 缺失不等于不适合
- 缺失字段只降低置信度，不直接剔除文档

建议每条食材额外保留：

```json
{
  "available_fields": [],
  "missing_fields": [],
  "coverage_score": 0.0
}
```

处理方式：

1. 原始层将缺失值保存为 `null`
2. 向量文本层只写入已有字段，不强行补 0
3. 重排时把 `coverage_score` 纳入评分
4. 若限制条件涉及的关键字段缺失，只做谨慎降权并标注风险

## 9. 向量库选型

当前项目数据量约为几千条食材，优先选择 `Chroma`：

- 本地部署轻量
- Python 接入简单
- 持久化容易
- 对当前数据规模足够快
- 方便后续替换 embedding 模型

当前实现采用：

- 向量库：`Chroma`
- 文档单位：单食材单文档
- 检索模式：向量召回 + 规则重排
- 默认向量化：中文语义 embedding，优先使用 `BAAI/bge-small-zh-v1.5`
- 回退策略：若中文模型不可用，则回退到本地稳定哈希向量，保证离线可运行
- 向量层与中间层解耦，可继续替换为其他中文 embedding 模型

## 10. 食材到菜品的软约束

中间层输出的是“强证据”，不是“硬白名单”。

约束原则：

- 优先参考高置信度候选食材
- 至少使用 1 到 2 个核心候选或其同类替代
- 允许加入少量常见辅料，让中国菜式自然成立
- 如果候选食材不适合直接成菜，可继承其营养方向，不必强行入菜
- 禁止为了贴合候选列表而生硬拼菜

## 11. 一级模型职责调整

一级模型的职责不再是单纯“优化提示词”，而是：

- 对输入做隐私脱敏
- 分析用户身体状态和心理状态
- 推断用户当前需要重点关注的营养素
- 生成知识库检索关键词
- 生成面向二级模型的优化提示词

推荐输出结构：

```json
{
  "用户画像摘要": "",
  "身体状态分析": "",
  "心理状态分析": "",
  "需重点关注营养素": [],
  "饮食限制": [],
  "检索关键词": [],
  "优化提示词": ""
}
```
